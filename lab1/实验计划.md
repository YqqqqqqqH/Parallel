## 1. 这台机器的四个特点（它们决定了实验怎么设计）

| 观察 | 对实验的影响 |
|---|---|
| **i7-14650HX = 8 个 P 核 + 8 个 E 核，共 24 线程**，但 WSL2 里 lscpu 显示为同构的 12 核×2 | "按 nnz 静态均分"默认每个线程一样快。线程落到 E 核或 SMT 兄弟线程上时，工作量均分了，耗时却不均。这是本机特有的、可检验的假设（见 E6）。报告里"物理核数"写 16，并说明 WSL 显示的拓扑不真实 |
| 默认矩阵 nnz=958,976，约 **11.5 MB < 30 MB L3** | 默认配置基本在 L3 里，测的是"缓存内的 SpMV"。要单独设计规模扫描，跨过 L3 进入 DRAM 带宽受限区（E4） |
| 没装 `perf`，WSL2 可能不暴露硬件 PMU | 先探测。没有 cycles/instructions 时，改用软件事件，并用"CPU 利用率 = task-clock / 墙钟时间"做分析（见 §5） |
| 笔记本 HX 处理器有功耗墙和温度墙 | starter 在一个进程里**按固定顺序**测各策略，排在后面的策略可能因为芯片变热而吃亏。用 `--only` 单独跑每个策略，并轮换运行顺序 |

## 2. 核心设计：2×2 析因 + 可证伪的上界模型

### 2.1 策略：两个独立维度，各取两个水平

| | **静态分配** | **动态分配** |
|---|---|---|
| **按行切分** | `student_1 --sched static`（与 std::thread 的分块方式完全相同） | `student_1 --sched dynamic,c / guided,c` |
| **按 nnz 切分**（长行可以拆给多个线程） | `student_2`：nnz 均分成 p 段，每段用二分查找定位起始行 | `student_3`：nnz 切成多个固定大小的块，`schedule(dynamic)` 领取 |

- 注册 3 个函数，每个都对应一个明确的实验问题：分配方式的效应、切分粒度的效应、两者的交互作用。
- `student_1 static` 和 `std::thread` 的分块方式**完全相同**，所以两者的时间差只来自线程管理，这正是 3.3 节要求的公平对照。
- 实现要点（student_2/3 相同）：
  - 每一行归"它起始位置所在的那一段"负责；为了处理 nnz=0 的情况，最后一段取闭区间。
  - 被拆开的长行，后续段算出的部分和写进 `carry[seg]`，并行区结束后串行把它们加回去（只有 O(段数) 次加法）。
  - 空行由负责它的段写 0，所以 `normal-nnz 0` 也能算对。
  - **按行切分的策略**累加顺序和串行一样，结果逐位相同。**按 nnz 切分的策略**改变了长行的累加顺序。按 PDF 3.1 的要求，报告里要说明这一点并给出实测的最大误差（预估在 1e-12 量级，容差约 1e-8）。

### 2.2 上界模型（记 W = 总 nnz，L = 最长一行的 nnz，p = 线程数）

- 按行切分时，没有任何调度能做到比 `max(W/p, L)` 更快，所以**加速比 ≤ min(p, W/L)**。
- 按行动态调度相当于贪心表调度，由 Graham 界，完成时间 ≤ `W/p + (1−1/p)·L`。
- 按 nnz 切分没有 L 这一项，理想完成时间约为 `W/p`，再加 O(p log n) 的定位开销。
- 按行静态分块的完成时间取决于**长行随机落到哪些块里**，可以直接从 `row_ptr` 算出"最重块的 nnz / 平均值"来预测。

三个代表性配置（数字已手算）：

| 配置 | W | L | W/L（按行切分的加速比上限） | 长行占比 | 数据量 |
|---|---|---|---|---|---|
| A 默认 | 958,976 | 20,000 | 47.9 | 67% | ≈11.5 MB |
| B README（16×80000） | 1,599,744 | 80,000 | 20.0 | 80% | ≈19 MB |
| C 极端（我设计的：1×100000，cols=2e5） | 419,968 | 100,000 | **4.2** | 24% | ≈5 MB |

**预测**：
- 在 C 上，`student_1` 无论用多少线程，加速比都会卡在 4.2 以下，而 `student_2/3` 不受这个限制。
- 在 B 上、p=16 时，按行动态调度最坏可能比理想慢约 1.75 倍。
- 在 A 上，按行动态调度和按 nnz 切分应该差不多。

这些预测会写进报告，后面的实验去检验它们。

## 5. perf 方法：差分重复次数法

PDF 里的示例命令会把矩阵生成、参考解计算、预热都算进计数器。对大矩阵来说，这些开销甚至比 SpMV 本身还大。修正方法如下：

```
perf stat -r 5 -e <events> ./csr_spmv_lab --only omp3 --repeats 20  ...
perf stat -r 5 -e <events> ./csr_spmv_lab --only omp3 --repeats 220 ...
```

两次计数相减再除以 200，就是单次 SpMV 的计数，固定开销正好抵消。比较对象是 serial、std::thread、omp1(static)、omp3。

- **探测**：先由用户执行 `sudo apt install linux-tools-common linux-tools-generic`（需要 sudo，我无法代为执行），再运行 `perf stat -e cycles,instructions true`。
- **有硬件事件时**：看 IPC、cache-misses，并换算成每个 nnz 的未命中数。
- **没有硬件事件时**：看 task-clock、context-switches、cpu-migrations、page-faults。由此推出 **CPU 利用率 = task-clock / 墙钟时间**：
  - 不均衡的 OMP 运行中，空闲线程会自旋等待（libgomp 的 spin），所以 task-clock 偏高，但其中大部分不是有用的工作。
  - std::thread 每次调用都会 clone，context-switches 应该会明显变多。
- 另外做一个小对照：`OMP_WAIT_POLICY=active` 和 `passive`，看自旋等待的代价有多大。
- 报告里写明哪些事件不可用，以及用什么替代。
