## 二、方案的选择

**2×2 设计与保留 omp2。** 2×2 的设计来自计划里的上界推导（计划由 Claude Code 给出）。留着 omp2 是为了控制变量：没有它，就分不清 omp3 的优势来自"拆开长行"还是"动态领取"。有了它，两个效应可以分别看：报告 E2 中 omp3 的加速比比 omp2 高 33%–48%，这是动态领取的贡献；长行占比 r（最长一行的工作量与每个线程平均工作量之比）大于 1 时 omp2 比 omp1 好，这是按非零元切分的贡献。

**最终选 omp3。** omp1 最坏时加速比比 omp3 低 76%（E2 中 L=160k，1.90 对 7.85），omp3 最坏时只比 omp1 低约 10%（L=2.5k，7.27 对 8.10）；omp3 在 20 个随机种子间的时间波动（变异系数）只有 2%–3%，omp1 约 5%。评分里有"鲁棒性"一项，这也是倾向它的原因。

## 三、遇到的 bug 及解决

以下 5 个问题都是 Claude Code 在实验中发现并修复的，按出现顺序列出。

1. **测试框架的隐患（未实际触发）。** 各策略共用同一个 output 数组，漏写的行会沿用上一个策略写下的正确值而通过检查。修正：检查前先把 output 填成 1e300。不能填 NaN，因为 NaN 与任何数比较都为假，"误差大于容差"不成立，漏写反而会通过（已用真实的 `check_result` 实测）。
2. **CSV 列错位。** 调度名 `dynamic,64` 自带逗号，使这类行的误差数据被读错，第一次统计的最大误差被低估了几十倍，但程序的通过/失败判定不受影响。修正：给该字段加引号，E0 重跑。
3. **测试用例写错。** "nnz 少于线程数"的用例忘了加 `--long-nnz 0`，默认值 20000 大于 `--cols 10`，参数校验直接拒绝，出现 31 次假失败。实现没有错，说明测试本身也会写错。
4. **测量顺序导致效率超过 1。** E1 第一次测得配置 B 的串行时间 T₁ 为 1.479 ms，单线程 OpenMP 的效率却超过了 1，这不合理：它多了线程管理开销，不可能比串行更快。原因是串行任务被排在所有多线程任务之后才跑。把任务顺序随机打乱后，T₁ 降到 1.172 ms，效率不再超过 1。这说明存在顺序效应，但没有证明是芯片升温造成的。
5. **perf 的上下文切换恒为 0。** 在 `perf_event_paranoid=2` 下，perf 只统计用户态事件（事件名带 `:u`），内核态的上下文切换被过滤，计数恒为 0，连每次调用都创建 16 个线程的 std::thread 也是 0。我执行 `sysctl` 把它调到 1 后，std::thread 每次调用约有 7.7 次上下文切换。
