# 心路历程

## 一、我是怎么完成这次实验的

和实验一一样，我主要依靠 Claude Code：它读题目和配套代码、写出实验计划，我审过后再让它实现、测试和跑实验；遇到需要取舍的地方，它停下来给出选项，由我决定。

数据走了弯路。一开始我没有找到题目所说的 `/var/dataset`，于是 Claude Code 用公开的 SIFT1M 按相同格式自建了一份数据，先用来开发和调试。后来问了助教，我才知道数据在实验服务器上，于是改用服务器上的官方数据。官方数据的 base、query、gt 与自建版本完全相同，只有中心和列表划分不同。报告里的所有计时，都在服务器上重新做了一遍。

和实验一一样，我在使用 AI 的过程中学习如何使用 AI。我体会到，在需要两个环境对照、而各部分又互不依赖的实验里（这次是笔记本和课程服务器），可以分出子 agent 并行推进。这次就分出一个会话，专门打通服务器，并在官方数据上做正确性检查和快速计时。另外，在对照 AI 给出的结果时，我也巩固了课上学到的知识。

## 二、方案的选择

- **omp1 用 dynamic:1**：16 线程、batch=64 时，static 比 dynamic:1 慢 30%（101.5 ms 对 78.2 ms）。各查询的候选数差别大，线程速度也不一样，动态领取能自动平衡。
- **omp2 的划分**：每个查询生成一个任务，任务内部再按 grain 切块，每块各自保留前 k 个，最后合并。grain 在 batch=1 时选 128，在 batch=64 时选 1024，服务器上实测这两个值都是最优。小任务阈值取大了会变慢，取小了也没有收益，所以不设。

## 三、遇到的问题和判断方法

1. **单查询时 omp2 比串行还慢**：中心选择占 63.7%，单查询时只能串行执行，所以加速比最多 1.52，但实测还低于这个值。对比两种等待策略后发现：自旋时，计算线程比串行慢 24%，是空转的线程拖慢了它；改成 passive 后，唤醒的开销更大，反而更慢。
2. **16 线程的加速比偏低**：笔记本上只有 7.4 倍。逐线程统计显示负载是均衡的，但每个线程都变慢了，我怀疑是 P/E 混合核造成的。换到服务器后升到 11.7 倍，基本印证了这个猜测；剩下约 28% 的减速，推测与虚拟机的超线程有关。
