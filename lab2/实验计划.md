## 1. 本实验特有的三个事实，以及由此得出的成本模型

### 事实 ①：中心选择是每个查询都要付的固定开销，而且通常比候选扫描还贵

- 中心选择要算 L·d = 4096×128 ≈ **52.4 万**次维度运算（标量 double）。
- nprobe=8 时，候选扫描约为 C(q)·d：
  - 列表平均长度 N/L = 244，所以 C 约为 8×244 = 1953。
  - 查询往往落在稠密区域，这里的列表偏长，预计实际 C 在 2000–4000 之间。
  - 对应的扫描量为 25–51 万次维度运算。
- 由此预计 **f_sel（中心选择占单查询时间的比例）≈ 0.5–0.7**。
- 题目规定"各实现应共用已有的标量中心选择函数"，所以这部分既不能用 SIMD 加速，在 batch=1 时也只能串行执行。

### 事实 ②：坐标都是整数，任何累加顺序算出的距离都完全相同

- SIFT 坐标是 0–255 的整数，每项 (q−x)² ≤ 65025。
- 128 维求和不超过 128×65025 ≈ 8.3×10⁶ < 2²⁴。由于每项都非负，**任何累加顺序下的中间和都是小于 2²⁴ 的整数**。
- 因此 float32 SIMD 算出的距离与标量 double 逐位相同。打乱累加顺序也不会改变 Top-k 的排序或等距时的次序。
- 这让我们可以用 float32 获得两倍的 SIMD 通道数（lane）。

### 事实 ③：这台机器上各线程速度不一样（Lab1 已测得）

- 机器是 8P+8E、WSL2 环境，vCPU 被映射到哪个物理核会在运行中变化。
- Lab1 测得：p=16 时线程平均速度是串行的 0.71 倍；绑核与否在 p≤16 时差异只有噪声大小；p=24 时会被其他进程抢占，出现双峰。
- 本实验中 **P = 16**（物理核数），大 batch 取 4P = 64。

### 单查询成本模型

```
W(q) = a                 （中心选择，与查询无关）
     + b · C(q)          （候选扫描，SIMD 只能加速这一项）
     + c · 块数(q)·k     （omp2 的合并开销）
     + 任务/线程管理开销
```

## 3. 实现（主要改 `ivf_student.cpp`；串行参考和 `check_result` 不动）

- **`SearchOptions` 新增字段**（在 `ivf_search.h` 中）：
  - `dist`：scalar / simd64 / simd32
  - `coarse`：lib / split
  - `cutoff`
  - `sched` 通过 `omp_set_schedule` 配合 `schedule(runtime)` 设置，不放进结构体。
- **SIMD 距离函数**：
  - `l2_simd64`：double 归约，`#pragma omp simd reduction(+:sum)`。
  - `l2_simd32`：float 归约，返回 double。
  - 启用 simd32 的前提由 harness 在计时之外检查：坐标都是整数，且 d·M² < 2²⁴（M 为坐标差的最大可能值）。不满足时拒绝运行，并在 CSV 中记录实际使用的模式。
  - Top-k 更新放在距离函数外面，各算各的，不放进归约循环。
- **omp1**：
  - `parallel for schedule(runtime)` 按查询划分，每个查询用自己的 `TopK`。
  - 实际参与的线程数为 min(p, count)，写入 CSV。
  - 用一次小消融（static、dynamic,1、guided）选定默认调度方式。
- **omp2**：一次调用只建一个线程团队。`parallel` + `single` 为每个查询生成一个查询任务 Tq，Tq 内部的步骤：
  1. 调用 `select_lists`（coarse=lib）。coarse=split 时，用 taskloop 分块，以 `l2_distance_scalar` 计算全部中心距离，再用同一个 `better` 选出前 nprobe 个。由于 `better` 是全序，选出的列表与 `select_lists` 完全相同，这一点也由完整的结果检查兜底。
  2. 把选中的 nprobe 个列表首尾相接，看作一个虚拟区间 [0, C)，用前缀和 off[] 定位每个列表的起点；按 grain 切成 nb 块，每块可以跨越列表边界。
  3. 若 C ≤ cutoff，直接串行扫描；否则对各块执行 `taskloop`（它自带隐式 taskgroup），每块维护一个局部 `TopK`，结果写入 `part[b·k, (b+1)·k)`。
  4. taskloop 结束后合并：跳过 id=−1 的条目，用 `finish` 补齐不足的位置。
- **omp2 必须注意的数据共享陷阱**：
  - `part`、`lists`、`off` 是 Tq 的局部变量。在嵌套的 taskloop 中，它们默认是 **firstprivate**，每个块任务会复制一份，写入的结果随副本丢失。
  - 因此全部使用 `default(none)`，并显式写出 `shared`。

| 对象 | 存放位置 | 谁写 | 谁读 | 何时释放 |
|---|---|---|---|---|
| lists / off | Tq 的局部 vector | Tq | 块任务（只读） | Tq 返回时；taskloop 的隐式 taskgroup 保证此前块任务已全部结束 |
| part[nb·k] | Tq 持有的 vector | 块 b 只写自己那 k 个位置 | Tq 在 taskloop 结束后读 | Tq 返回时 |
| output 中第 q 段 | 调用者传入的 output | 只有 Tq 写 | harness | — |

- **为什么每块只需保留 k 个**（报告中要给出证明）：设 e 在全局排在前 k 名，则全局比 e 更好的元素不超过 k−1 个，在 e 所在的块里更好的元素也就不超过 k−1 个，所以 e 一定在本块的前 k 名中。前提是 `(distance, id)` 构成全序，且 id 不重复。
- **omp3（反面对照）**：任务划分与 omp2 相同，但每个候选都在 `critical` 中更新共享的 TopK。只在少量查询（小 Q）上运行，用来量化同步开销。
- **std::thread**：
  - 每次调用创建 min(p, count) 个线程，按连续区间分配查询，划分方式与 omp1-static 完全相同；返回前 join 回收线程。
  - 只使用 `select_lists` 和 `l2_distance_scalar`，与串行版本相同。

## 7. perf：用 `--control` 只统计检索部分

- **命令**：
  ```
  perf stat --delay=-1 --control fifo:ctl,ack -e <events> ./ivf_lab ... --perf-ctl ctl,ack
  ```
  使用 `/usr/lib/linux-tools/6.8.0-147-generic/perf`。
- **对象**：serial、omp1、omp2、std，p=16，batch=64。
- **事件**：
  - task-clock、context-switches、cpu-migrations、page-faults；
  - cycles、instructions、cache-misses、branch-misses 也尝试采集。WSL 预计显示 `<not supported>`，原始输出照样保存，报告中如实说明。
- **采集前**：请用户执行 `sudo sysctl -w kernel.perf_event_paranoid=1`。否则上下文切换会被 `:u` 过滤，计数为 0。
- **验证是否覆盖了工作线程**：OpenMP 运行时 task-clock/墙钟应接近 p（空闲线程在自旋等待）；关闭控制时的计数应接近 0。
- **换算**：
  - 每个查询的 task-clock，以及 CPU 利用率；
  - std::thread 每次调用的缺页次数（新线程的栈）和上下文切换次数，用来解释 P8。
- **带宽**：没有硬件计数器时，"是否受内存带宽限制"改用有效带宽回答：候选数×512 B / 扫描时间，与一个小型读带宽探针（`bw_probe.cpp`）测得的峰值比较。这回应了题目中"仅凭 cache-misses 不能判断带宽是否用满"。
